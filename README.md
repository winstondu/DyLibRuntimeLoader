# DyLibRuntimeLoader

DyLibRuntimeLoader provides plugin systems for Swift through dynamic libraries loaded on demand, with Swift macros that make invocation signatures build-time checked instead of relying on handwritten symbol strings and untyped casts.

![A binary being loaded dynamically from storage into memory](res/sc_5.jpeg)

**Platforms:** macOS 10.15+ · iOS 13+ · Swift 6 toolchain (`swift-tools-version: 6.0`)

## How it works

Define the shared interface:

```swift
import DyLibRuntimeLoader

@DyLibInterface
public protocol Animal {
    func speak() -> String
}
```

`@DyLibInterface` generates an `AnimalPluginSpec` enum whose interface type and symbol name (`__dylib_entry_Animal`) are derived from `Animal`.

Implement that interface in a plugin:

```swift
import AnimalInterface
import DyLibRuntimeLoader

@DyLibExport(Animal.self)
public struct Cat: Animal {
    public init() {}
    public func speak() -> String { "Meow" }
}
```

`@DyLibExport` generates the matching `@_cdecl` entry point and a factory that returns the implementation as `any Animal`.

Load it from the host:

```swift
import AnimalInterface
import DyLibRuntimeLoader

let cat = try AnimalPluginSpec.load(from: catPath)
print("Cat: \(cat.speak())")
```

`AnimalPluginSpec`, generated by `@DyLibInterface`, gives the host a fully typed `load(from:)` call returning `any Animal`.

At compile time:

- The symbol name is never hand-typed; both macros derive it identically from the interface name.
- The exported type's conformance to the interface is checked.
- The exported type must provide an accessible zero-argument `init()`.
- The host loads and invokes a fully typed interface.

At runtime:

- The fixed-layout entry header's magic and ABI version must be valid before the loader interprets its Swift object box.
- The entry's spec type must have the same Swift metadata identity as the host's spec. This catches a wrong-spec entry and mispackaged or statically duplicated interface modules. An older plugin built against the same dynamically loaded interface module retains that metadata identity and is not detectable by this check alone.

## Versioning interfaces

Adding protocol requirements requires rebuilding every plugin. Bump the macro version on the interface and each updated plugin—for example, `@DyLibInterface(version: 2)` and `@DyLibExport(Animal.self, version: 2)`—to derive a new entry symbol. An outdated plugin then fails explicitly with `symbolNotFound` instead of being invoked with a stale witness table. Swift library evolution is the advanced alternative when compatible evolution across independently built images is required.

## The golden rule

Every interface module and `DyLibRuntimeLoader` itself **must be a `.dynamic` library product shared by the host and every plugin; never statically duplicate them**. Swift type identity is metadata identity, not just a module-qualified spelling. Two static copies of the same source create distinct protocol, spec, and runtime metadata, so values crossing the dynamic-library boundary are not the same Swift types. Ship and load one process-wide copy of each shared module.

Dynamic linking loads the host's declared shared libraries as part of process startup; dynamic loading uses `dlopen` later, when a feature is needed. Small interface modules keep the host and plugins decoupled and can also reduce rebuilds, as described in SwiftRocks' [Interface Modules](https://swiftrocks.com/reducing-ios-build-times-by-using-interface-targets). This architecture is related to the dylib and generated-plugin approach discussed in [The evolution of Facebook's iOS app architecture](https://engineering.fb.com/2023/02/06/ios/facebook-ios-app-architecture/).

## Dependency graphs

Describe a plugin and the libraries it needs with `DyLibLibrary(path:dependencies:)`:

```swift
let dogLibrary = DyLibLibrary(
    path: dogPath,
    dependencies: [DyLibLibrary(path: trickPath)]
)
let dog = try AnimalPluginSpec.load(from: dogLibrary)
```

`DyLibLoader` computes a topological order and opens dependencies before their dependent library. A cycle throws `DyLibError.dependencyCycle` with the cycle path. The process-wide `DyLibLoader.shared` registry owns handles and reference counts, so a plugin may load another plugin through the same registry; the [Dog plugin](Examples/DogPlugin/Sources/DogPlugin/Dog.swift) loads the [Backflip plugin](Examples/BackflipPlugin/Sources/BackflipPlugin/Backflip.swift) through `TrickPluginSpec`.

`DyLibLibrary` defaults to `.now`, `.local`, and `.first`; `RTLD_FIRST` confines handle-based symbol lookup to the requested image rather than its dependencies. Supply `DyLibOpenFlags` to opt into other `dlopen` behavior. The registry is keyed by canonical path, so the flags from the first open win while that image remains resident.

## Client connections

Declare a typed connection at file scope in the app and use its interface directly:

```swift
@DyLibConnect(Animal.self, framework: "AnimalImplementation")
enum DogPlugin {}

print(DogPlugin.instance.speak())
```

`DogPlugin.instance` is an `any Animal` lazy proxy. Accessing the proxy does not load the framework; its first method call or property read resolves the framework path and loads the plugin. The proxy itself is cheap and stateless, while `DyLibLazyPlugin` caches the first successful instance. Resolution is thread-safe, concurrent first calls collapse to one load, and failures are not cached, so the next call retries. `DogPlugin.isLoaded` reports whether an instance has been cached.

For throwing interface requirements, a load failure is returned as the thrown error. A non-throwing method or property cannot surface a load error through its signature, so its proxy traps with a message containing the interface name and the load error. When a caller needs to handle loading failure gracefully before invoking a non-throwing requirement, use `try DogPlugin.loadIfNeeded()` explicitly.

Connections work inside plugins too, allowing one plugin to load another only when needed:

```swift
@DyLibConnect(Trick.self, framework: "TrickImplementation")
enum TrickPlugin {}

@DyLibExport(Animal.self)
public struct Dog: Animal {
    public init() {}
    public func speak() -> String { "Woof! (and does a \(TrickPlugin.instance.perform()))" }
}
```

Lazy proxies are generated by default because `@DyLibInterface` can inspect the protocol requirements. Use `@DyLibInterface(proxy: false)` to generate only the plugin spec. Connections to a proxy-less interface must use `loadIfNeeded()`; their generated `instance` member is intentionally unavailable because no `<Interface>LazyProxy` exists.

Proxy generation does not support initializer or static requirements, mutating functions, settable properties, subscripts, or associated types. If any of these appear, the macro diagnoses the named requirement, still generates the plugin spec, and skips the entire proxy. Apply `proxy: false` when the interface intentionally uses one of these shapes.

`DyLibLibrary.framework("AnimalImplementation")` follows the app-bundle convention `Frameworks/AnimalImplementation.framework/AnimalImplementation` (including the macOS `Contents/Frameworks` layout). Connection dependencies become library dependencies and load first:

```swift
@DyLibConnect(
    Animal.self,
    framework: "AnimalImplementation",
    dependencies: [TrickPlugin.self]
)
enum DogPlugin {}
```

## Run the example

```sh
git clone https://github.com/winstondu/DyLibRuntimeLoader.git
cd DyLibRuntimeLoader
Examples/run.sh
```

Expected output:

```text
Cat: Meow
Dog: Woof! (and does a backflip)
Expected output verified.
```

The script builds each package independently, then colocates the host and exactly one copy of every shared dynamic library in `Examples/.dist`.

## Developing and testing

```sh
swift build
DYLIB_DEV=1 swift test
```

The `DYLIB_DEV=1` manifest gate adds test targets, test-only dependencies, and linker flags only for maintainers, keeping them out of consumer dependency resolution and builds.

## Error handling

All v2 loader failures are represented by `DyLibError`:

| Case | When it fires |
| --- | --- |
| `failedToOpen(path:reason:)` | `dlopen` cannot open an image, for example because the path is missing or the binary is incompatible. |
| `symbolNotFound(symbol:path:)` | The library opened, but `dlsym` cannot find the spec's generated entry symbol. |
| `invalidEntry(symbol:path:)` | The entry symbol returned a boundary header with the wrong magic value. |
| `abiMismatch(expected:found:)` | The plugin entry reports a different `DyLibABI` version from the runtime. |
| `specTypeMismatch(expected:found:)` | The plugin's spec metadata is not identical to the host's, or its factory value cannot be cast to the expected interface; this catches wrong-spec entries and duplicated interface modules. |
| `dependencyCycle(path:)` | A `DyLibLibrary` dependency graph contains a cycle. |
| `notLoaded(path:)` | An operation receives a closed, stale, or otherwise unregistered library handle. |

## Unloading

`load(from:)` deliberately follows the load-and-keep policy and does not expose its acquired handle. When explicit release is required, use `loadWithHandle(from:)`, then pass its handle to `DyLibLoader.close(_:)` after the instance and every other image value are gone. Unloading Swift code is unsafe while any instance, closure, witness table, or type metadata from that image remains alive.

## iOS and the App Store

Loading executable code that is signed, embedded, and shipped inside the submitted app bundle is compatible with this design. Downloading, installing, or executing new code that introduces or changes app functionality at runtime violates [App Store Review Guideline 2.5.2](https://developer.apple.com/app-store/review/guidelines/#software-requirements). Follow the normal code-signing, embedding, and review requirements for every shipped image.

A missing dynamically linked interface or runtime library prevents process launch; a missing on-demand plugin lets the host launch and produces `failedToOpen` when requested. The deprecated `FrameworkName` API remains available for bundle-based paths, and now selects an XCFramework slice by parsing its `Info.plist` rather than hardcoding slice directories.

## Migration from v1

| Deprecated v1 API | v2 replacement |
| --- | --- |
| Handwritten `@_cdecl("symbol")` plus `dyLibCreator(factory:forType:)` | Attach `@DyLibExport(Interface.self)` to the implementation. |
| `dyLibLoad(withSymbol:fromPath:forType:)` | `InterfacePluginSpec.load(from: path)` |
| `dyLibLoad(withSymbol:fromFramework:forType:)` | Resolve the executable path, then call `InterfacePluginSpec.load(from: path)` or pass a `DyLibLibrary`. |
| `dyLibLoad(fromPath:)` | `DyLibLoader.shared.open(DyLibLibrary(path: path))` |
| `dyLibLoad(fromFramework:)` | Resolve the executable path, then call `DyLibLoader.shared.open(DyLibLibrary(path: path))`. |
| `FrameworkName` and `Directory` | `DyLibLibrary(path:dependencies:)` with a direct executable path. |
| `DynamicFrameworkLoaderError` | `DyLibError` |
